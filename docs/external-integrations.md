# API keys and webhooks

## Enable

Apply Alembic revision `20260917_0023` with `alembic upgrade head` from `backend/`. The migration is additive and grants `integrations.manage` to the system admin role. Existing tenant data is preserved. This change does not run migrations against an operational database automatically.

Set `INTEGRATIONS_ENCRYPTION_KEY` to a Fernet key in the **same private environment for the API and scheduler**. Generate it locally with:

```sh
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Back up this encryption key separately from the database. Webhook secrets are encrypted at rest with this key; missing/invalid configuration prevents webhook creation and fails delivery closed. Do not replace the encryption key without re-encrypting existing endpoint secrets. Endpoint secret rotation is a separate operation and does not change the encryption key.

Run the existing dedicated scheduler (`python -m app.scripts.scheduler`, one replica). It processes up to 25 due deliveries per company every minute; document expiry events are generated by the document compliance scan. No outbound webhook request runs in a domain transaction.

Admin pages:

- `/admin/integrations/api-keys`: create, show once, revoke, rotate, expiry and last use.
- `/admin/integrations/webhooks`: create, show signing secret once, revoke, rotate, inspect paginated deliveries and resend.

The pages and APIs require unrestricted `integrations.manage`. The default fleet-manager role does not receive this permission. Delegated administrators must also hold all unrestricted domain permissions associated with scopes they issue. Endpoints subscribe to company-wide events, so grant this administrative permission accordingly.

## API keys

Send `Authorization: Bearer vfc_…` to the existing `/api/v1` endpoints. Each key contains 256 random bits; only its SHA-256 digest and display prefix are stored. The raw key appears only in the successful create/rotate response, never in a list, audit record, or persistent browser storage. API responses carry `Cache-Control: private, no-store`.

| Scope | Allowed methods and paths relative to `/api/v1` |
| --- | --- |
| `vehicles.read` | GET `/vehicles`, `/vehicles/{id}` |
| `drivers.read` | GET `/drivers`, `/drivers/{id}` |
| `fuel.write` | POST `/fuel` using the existing multipart contract |
| `maintenance.read` | GET `/work-orders`, `/work-orders/{id}`, `/services/history`, `/services/reminders`, `/services/id/{id}`, `/maintenance/summary` |
| `maintenance.write` | POST `/work-orders`, `/work-orders/{id}/complete`, `/services`, `/services/register-with-bill`, `/services/upload-bill-later`; PUT `/work-orders/{id}`, `/work-orders/{id}/status`, `/services/id/{id}` |
| `reports.read` | GET the explicit report names in `app/services/api_keys.py`, including their `/export` endpoints |

Write scopes include the read permission required by those routers, but do not enable their GET routes. API keys cannot call admin, auth, mobile, file download, bulk/import, or other unlisted routes. Existing request formats and business validation still apply.

Authentication validates the key, expiry, revocation, company, active creator and active membership on every request. It intersects the key's permissions with the creator's current grants. Organizationally scoped domain grants fail closed for external keys because some existing detail/report routes do not consistently enforce these scopes. Removing membership, disabling the user/company, or requiring a password reset disables keys too. Company comes exclusively from the key. Key rotation atomically revokes the old key and returns a new one with the same scopes and expiry, attributed to the administrator rotating it.

API keys are bearer credentials; possession permits repeated calls until expiry or revocation. They are not one-time request nonces. Mutation clients should not retry non-idempotent operations blindly after a timeout; existing business duplicate checks still apply. Prefer expiring credentials and rotate them when access changes.

## Events and transactions

Supported events:

```text
vehicle.created       vehicle.updated       driver.created
assignment.started    assignment.completed  inspection.failed
work_order.created    work_order.completed  service.created
fuel.created          document.expiring     reservation.approved
accident.reported     claim.updated
```

ORM flush hooks capture new rows and state transitions, including writes through imports, mobile and shared services. They create the outbox in the same transaction; rollback removes deliveries. Bulk SQL or raw SQL bypasses ORM hooks: new domain writers using those mechanisms must explicitly call `enqueue_event` in their transaction. There is no historical backfill. An event can be emitted for each real transition within a transaction; recipients should use the supplied snapshot and fetch current data when needed.

`document.expiring` is emitted once per endpoint/document/expiry while an unarchived document is within 30 days of expiry, including expiry today. It is independent of in-app notification preferences. Renewal to a different expiry permits a new event. A single scheduler replica is required for scan coordination.

Payloads contain exactly the envelope below. `data` is an allowlisted projection of status and related IDs/mileage/completion, or document expiry and owner IDs. It excludes personal contact details, free text, file paths, costs, credentials and tokens.

```json
{
  "event_id": "UUID shared across subscribers and retries",
  "event_type": "assignment.started",
  "company_id": 1,
  "occurred_at": "2026-09-17T12:00:00.000000Z",
  "entity_id": 42,
  "data": {"status": "Active", "vehicle_id": 5, "driver_id": 8}
}
```

## Signing and receiver contract

Headers:

```text
X-VFC-Event: assignment.started
X-VFC-Delivery: <delivery UUID>
X-VFC-Signature: t=<Unix seconds>,v1=<HMAC-SHA256 hex>
```

The signed bytes are `timestamp + "." + delivery_id + "." + exact_request_body`. The HMAC key is the UTF-8 signing secret, including its `whsec_` prefix. Always verify the original bytes before JSON parsing. `app.services.webhooks.verify_signature` is a reference verifier with a five-minute timestamp window and constant-time comparison. The timestamp is refreshed on every attempt; `occurred_at` remains the event time.

Receiver processing must:

1. Verify the signature and timestamp using a trusted current secret. Check `X-VFC-Event` equals the signed payload's `event_type`, and validate the expected `company_id`.
2. Insert `(company_id, event_id)` into a durable inbox with a unique constraint **in the same transaction as business processing**. On an existing ID, return a success response without processing again. A delivery ID alone is insufficient because manual resends receive new delivery IDs.
3. Return 2xx only after durable acceptance. Freshness checks reject old captured requests; the inbox rejects duplicate/replayed events inside the timestamp window and across resends. Signature verification by itself does not prevent duplicate processing.

Secret rotation immediately replaces the stored secret and increments its version. New attempts, including retries of queued events, use the current secret. An already in-flight attempt can use the prior version; receivers may temporarily accept the previous secret for the timestamp window while deploying the replacement. Attempt history records which version signed each attempt. A failed or lost one-time rotation response requires another rotation.

## Delivery and SSRF protections

Pending → Retrying (leased in flight) → Delivered or Failed. Failures become due after 30, 60, 120, 240 and 480 seconds; the sixth unsuccessful attempt becomes Dead. The minute-based scheduler sets the actual dispatch granularity. HTTPS 2xx is success; redirects, other HTTP statuses and transport failures count as failures. Revoked endpoints stop future sends and their pending deliveries become Dead. Requests already in flight may complete.

Claims use an atomic conditional update and a two-minute lease. Claims and attempt records commit before network IO. Expired claims recover; interrupted sends count toward the attempt limit. Delivery is **at least once**, with no ordering guarantee: a crash after receiver acceptance and before success persistence may cause duplicate delivery.

Manual resend creates a new delivery with a new UUID and a link to the original; it preserves the event ID and exact payload. The original attempts remain inspectable. Resending a Failed delivery ends its automatic retry series. Active/in-flight or revoked deliveries cannot be manually resent. History is paginated by `before_id`, with at most 100 deliveries per response; no automatic retention purge is implemented.

Only public HTTPS URLs on port 443 are accepted. Credentials, fragments, malformed/control characters, private/loopback/link-local/reserved/multicast IPs, mapped IPv6 and transition addresses are rejected. All DNS answers must be public. DNS is checked both on registration and every attempt; the connection uses the validated numeric address with the original hostname for SNI and certificate verification. Redirects and automatic HTTP retries are disabled, environment proxies are not used, connection/read timeouts are bounded, and response bodies are not read or stored. Transport details follow [urllib3's custom SNI guidance](https://urllib3.readthedocs.io/en/stable/advanced-usage.html#custom-sni-hostname).

## Verification

`backend/tests/test_integrations.py` exercises real HTTP dependencies with disposable SQLite databases, hashing, one-time disclosure, permissions, tenant isolation, expiry/revocation/rotation, all domain event transitions, rollback, URL policy, pinned transport options, signature tampering/freshness, retry/history/resend, leases, expiry deduplication and fresh/populated migrations. Outbound network responses and DNS are controlled test doubles; no external endpoint is contacted.

`frontend/tests/integrations.spec.ts` covers creation, one-time display, rotation, revocation, history/resend and permission gating with mocked APIs. Run the usual frontend build/lint/localization checks as well. Production PostgreSQL, real DNS/TLS and destination receiver acceptance should also be verified in staging before enabling customer integrations.
